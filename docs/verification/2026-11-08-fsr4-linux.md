# FSR 4 v07 on Linux — The Order: 1886 (CUSA00035, update 1.02) — 2026-11-08

## What was built

The runtime already carried the FSR 4 v07 INT8/DOT4 provider (FireBurn/FSR-Vulkan
`ffx_vk_fsr4_v07`, submodule c64f093) and the capability probes, but the Order temporal
integration was refused before the device query ("disabled in this build", #12) and the
provider modules were Windows-only DLLs. This build:

- `gpu/upscalers/fsr4/order1886_fsr4.cpp` — new provider on the existing OrderUpscale ABI:
  loads the v07 bundle, selects the model preset from render/output ratio, maps the game's
  color/depth/velocity targets (RGBA16F / R32F / RG16F) into the provider's import contract,
  and retires history slots only at the host-proven present watermark.
- `gpu/shim/order1886_upscale.h` — ABI 2: `OrderUpscaleFrame` gains `gpu_frames_completed`
  (appended; prefix-compatible). Providers must not retire descriptor/history slots before
  the GPU proves the frame finished; the presenter's waited present fence is that proof.
- `vk_upscale_providers.cpp` — POSIX dlopen (`order1886_fsr3.so`, `order1886_fsr4.so` next
  to the runtime binary), fsr4 provider entry, `/proc/self/exe` path resolution.
- `ps4gpu.cpp` / `vk_presenter.cpp` — the hardcoded `ConfigureUpscalerSupport(false, …)`
  is replaced by the real device probes (`IsFsr4Int8Supported`, `IsFsr411Supported`) after
  device creation, before any provider loads; unsupported requests still fall back to FSR 3.1.
- `vk_order_resolve.cpp` + `order_resolve_prep.comp` — the v07 bundle is compiled with
  `DEPTH_INVERTED=0`, so the prep pass flips The Order's reversed depth (push field
  `invert_depth`) only when the provider is fsr4. FSR 3.1/DLAA keep their flag path.
- `build.sh` — Linux builds both provider modules; launcher `order1886.py`/
  `order1886_options.py` — `fsr4` selectable in Graphics → Upscaling on Linux.

## Asset provenance

v07 INT8/DOT4 bundle: FireBurn/Q2RTX `baseq2/fsr4_shaders` — AMD MIT-licensed source-v07
shaders compiled to SPIR-V (`libdxcompiler 1.10(5322-c64a5165)`), per-preset SHA-256
manifests, `initializers.bin` 89,216 B + `pre_weights.bin` 1,024 B verified against the
provider contract. Installed at `bin/fsr4/` (285 files, 45 MB). Not AMD FSR 4.1.1:
`VK_VALVE_shader_mixed_float_dot_product` is absent from Mesa 26.2.6 RADV, so the 4.1.1
probe correctly reports unsupported.

## Device evidence (RX 9070 XT, RADV GFX1201, Mesa 26.2.6, Vulkan 1.4.354)

- Features: shaderFloat16, shaderInt8, shaderInt16, shaderIntegerDotProduct,
  computeDerivativeGroupLinear, shaderStorageImageExtendedFormats — all true.
- Boot log: `Upscaler provider fsr4: AMD FSR 4 v07 INT8/DOT4 (source) available`;
  `Upscaler: fsr4 requested; AMD FSR 4 replaces the game's temporal resolve`.
- Session: `Upscaler: fsr4 reconstructed 5400 frames (1920x1080, 2 samples, velocity scale 16)`
  over a 120 s run — the resolve replacement held for the whole session; no dispatch
  failures, no fallback to the game's resolve after arming.

## Tests

1. Offscreen GPU smoke (`order1886_fsr4_gpu_smoke --run-gpu`): same synthetic fixture as the
   FSR 3.1 smoke (128×72 → 256×144, 8 frames, validation layer): output finite, non-black,
   spatially varying; **0 validation errors**; clean destroy after fence completion.
2. In-game sessions at fixed timing (menu shot t+60 s, Continue, gameplay shots t+107/112 s),
   FSR 1 baseline vs FSR 4, same save (Chapter I courtyard), F12 presenter screenshots at
   2560×1440. The provider replaced the resolve for the whole session:
   `replaces The Order's temporal resolve at 1920x1080 (native, depth inverted 0)`,
   `fsr4 reconstructed 7200 frames (1920x1080, 2 samples, velocity scale 16)` ≈ 53 FPS.
   Detail metrics on same-scene pairs (camera drifts a few steps, so absolute gradient
   differs; high-frequency measures are the signal):

   | frame | grad | Laplacian power | edge energy |
   | --- | --- | --- | --- |
   | FSR 1 play1 | 3.75 | 119.6 | 455.0 |
   | FSR 4 play1 | 3.84 | **150.6 (+26%)** | **540.1 (+19%)** |
   | FSR 1 play2 | 4.48 | 139.1 | 438.1 |
   | FSR 4 play2 | 4.05 | **164.5 (+18%)** | **536.2 (+22%)** |
3. Shader integrity: the provider consumes the game's own resolve inputs; every game draw
   pass (shadows, GI, MSAA resolve to the inputs) is untouched. Baseline vs FSR4 frames show
   identical lighting, shadow placement and exposure; cobblestone cracks, awning stripes and
   fountain edges are visibly crisper; no ghosting on flag/fence edges, no disocclusion smear.
4. Fallback: with `upscaler=fsr4` on a device lacking the features the runtime logs
   `GPU does not support the selected FSR 4 shaders; using FSR 3.1` before the first frame
   (probe path); with the bundle missing the provider reports
   `FSR 4 v07 asset bundle … not found` and the game's own resolve stays — TBD verify.

## Known limits

- Model preset is chosen at context creation from the configured render/output ratio;
  dynamic resolution mid-session would need re-creation (not exercised: Order renders at a
  fixed internal size here).
- The v07 bundle is the FSR 4.0-era ML2Code model, not AMD's signed 4.1.1 provider.
- Camera near/far/fov arrive as the shim's documented placeholders; velocity is the game's
  own decoded pixel motion (same inputs the FSR 3.1 path uses).
- 60 FPS sessions can show QTE softlock risk in Chapters 6/9 (upstream warning, unchanged).
